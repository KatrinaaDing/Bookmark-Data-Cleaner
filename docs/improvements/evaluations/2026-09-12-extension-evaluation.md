# Extension evaluation — 12 September 2026

> Historical assessment of the checkout identified below. Findings may have been addressed later; see the [latest evaluation](2026-09-19-extension-evaluation.md) and [history index](../README.md).

The extension has a useful, focused purpose: remove unwanted bookmarks together with the browser data associated with their websites. Keep that purpose central. The architecture is appropriately small, and the current visual design is sufficient. The best investment is safer deletion, faster identification of old bookmarks, and clearer confirmation.

This review follows the owner's clarification that the extension is publicly distributed. It evaluates checkout `a4f964e`, version **3.0.0**. The [matching Chrome Web Store listing](https://chromewebstore.google.com/detail/bookmark-data-cleaner/fgbajdlddblimpajlokkmkdngpnmmaja?hl=en) returned during review shows **2.2**. The published package was not downloaded or executed; the reproduced defects below should not be attributed to version 2.2 without checking it.

## Confirmed defects, in priority order

### 1. [P1] Cookie deletion can exceed the reviewed scope

**Location:** `extension/browser/site-data.ts:71–85`; promise shown at `extension/components/cleanup-dialog.ts:159`.

In a fresh browser profile, created two cookies named `same`, both at `/`: a parent-domain cookie for `.collision.test` and a host cookie for `login.collision.test`. Selected only the latter through the site's inventory record. Calling the current removal function deleted **both**, with no reported error.

A second probe reviewed a cookie at `/path`, removed it before cleanup, and then created a same-name cookie at `/`. Cleanup deleted this new, unreviewed cookie and reported success.

The code supplies URL, name, store, and partition to `cookies.remove`; checking whether the intended identity remains afterward cannot detect collateral removal. Chromium's implementation builds a deletion filter from URL and name rather than the application's full identity tuple. See the [Chromium implementation](https://raw.githubusercontent.com/chromium/chromium/main/chrome/browser/extensions/api/cookies/cookies_api.cc).

**Recommendation:** fix this before releasing the reviewed build. Investigate identity-preserving expiry/deletion with the original required metadata. If exact targeting cannot be assured for a case, refuse that ambiguous operation or accurately review its broader scope. Skip already-absent targets. A preflight alone does not eliminate a concurrent cookie-change race, so do not claim it guarantees exact deletion. Add browser regressions for parent/child domains, overlapping paths, absent targets, and partition isolation.

**Value:** very high. **Effort:** medium. This protects the extension's central trust promise.

### 2. [P1] Options can change while a cleanup plan is being prepared

**Location:** `extension/components/cleanup-dialog.ts:107–114`.

Preparation receives a copy of `options`, but the final plan uses the live `options` object. The category checkboxes remain enabled during preparation. In a controlled delayed-preparation probe, preparation started with cookies off; enabling cookies while it waited produced a review that included cookie cleanup with an empty cookie inventory.

Consequently, a combined cleanup could report that category complete and remove bookmarks even though cookies were never discovered for the plan.

**Recommendation:** take one immutable options snapshot for preparation and plan creation; disable the choice controls while preparing. Add a focused regression for changing options during the await.

**Value:** high. **Effort:** small.

### 3. [P1] Site inventory blocks the UI for large collections

**Location:** `extension/core/inventory.ts:33–45`; repeated per-bookmark enrichment also occurs at `:84–93`.

Inventory repeatedly parses every history and bookmark URL for each site. This synchronous work runs in the app page. Synthetic measurements in the disposable Edge browser were:

| Sites | History entries | Bookmarks | Inventory computation |
|---:|---:|---:|---:|
| 100 | 1,000 | 1,000 | 151 ms |
| 500 | 5,000 | 2,000 | 2,640 ms |
| 1,000 | 10,000 | 2,000 | 9,307 ms |

These are single-run diagnostic measurements, not predictions for the owner's library or all machines. They exclude browser reads and rendering, but already demonstrate a substantial main-thread stall.

**Recommendation:** parse each URL once, index metadata by host, and retain the existing parent-domain matching semantics. Enrich duplicate bookmarks once per host. Measure again before adding workers, virtualization, or a framework. Detached construction of 2,000 bookmark rows took only 13 ms in this probe; that does not measure layout, but it does not support starting with complex virtualization.

**Value:** high for larger profiles. **Effort:** small to medium.

### 4. [P1] Details can open outside the visible window

**Location:** `extension/components/details-drawer.ts:98–104`; `extension/styles/drawer.css:23–24`.

At a 700 × 850 desktop viewport with 40 bookmarks, opening the first bookmark placed the details panel **2,225 pixels below the viewport's top**. Scroll remained at zero while keyboard focus moved to the invisible Close details button. The narrow layout appends details after the entire list and explicitly prevents focus from scrolling them into view.

**Recommendation:** ensure details become visible on opening. The smallest correction is deliberate scrolling in stacked layouts, with sensible return behavior. An inline panel beside the selected row or a narrow-window modal is a larger alternative; choose only if the simpler correction is awkward. Also check opening a row far down a desktop list.

**Value:** high for narrow windows and keyboard users. **Effort:** small for visibility correction, medium for a different layout.

### 5. [P2] Details remain stale after successful cleanup

**Location:** `extension/pages/sites.ts:169–193,230–235`; shared drawer content in `extension/components/details-drawer.ts`.

Through the actual selection → review → confirm flow, removed a site's only cookie. Results reported success and the site's row disappeared after refresh, but the open details panel still reported **1 detected cookie**. Saving a bookmark can similarly leave summary metadata unchanged.

**Recommendation:** reconcile the inspected record after refresh. Update the panel when the record remains; close it or show a concise updated state when it no longer exists. Preserve the existing focus-restoration behavior.

**Value:** medium to high; prevents apparent contradictions after destructive work. **Effort:** small.

### 6. [P2] Missing cookie access is displayed as zero cookies

**Location:** `extension/pages/bookmarks.ts:92–98`; `extension/components/site-details.ts:57–60`.

With the unmodified manifest and cookie permission absent, opening a bookmark showed **Detected cookies: 0**. The code substitutes an empty array for an unread inventory. Zero implies a measurement that never occurred.

**Recommendation:** carry availability separately from count and display “Not checked — cookie access is off.” Keep “0” for a successful scan that found none. Preserve optional access.

**Value:** medium. **Effort:** small.

### 7. [P1 accessibility] Unchecked checkbox boundaries have insufficient contrast

**Location:** `extension/styles/app.css:687–693`.

The custom checkbox border `#9ba8b8` has approximately **2.42:1** contrast against white and **2.19:1** against the selected-row tint. Because the extension replaces native rendering and the outline identifies the unchecked control, this falls below the **3:1** requirement for essential control visuals in [WCAG non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html).

**Recommendation:** darken the unchecked border enough to meet 3:1 on both backgrounds. Preserve the existing forced-colors fallback. Main text colors checked well: muted text is approximately 5.47:1 on white, and the blue accent 5.84:1.

**Value:** medium, particularly for public accessibility. **Effort:** very small.

There are seven verified findings: five P1 and two P2. P1 here means address before distributing this build broadly; severity is not an estimate of how often every user encounters it.

## Product improvements with the best return

| Order | Improvement | User value | Complexity and maintenance | Recommendation |
|---:|---|---|---|---|
| 1 | Bookmark search plus a simple age/last-opened filter | Very high: helps users find the old bookmarks the product promises to clean | Small for search; medium for filtering while preserving folder context and selection | Build next after correctness fixes |
| 2 | Better combined-cleanup review | Very high: users understand which bookmarks disappear and what website data is shared | Small to medium | Show total bookmarks/sites, retained bookmarks on affected sites, and exact removable bookmark titles/paths |
| 3 | Download a bookmark backup before removal | High: accidental bookmark deletion becomes recoverable | Small to medium for browser-importable export; higher for a full undo system | Start with export; do not promise restoration of cookies or site storage |
| 4 | A clear combined-cleanup preset with advanced categories | High: matches the main task and reduces repeated category choices | Small to medium | Keep bookmark removal explicit and keep final confirmation; never silently enable it from remembered settings |
| 5 | Clear selection, Back in review, and selection counts that expose hidden selections | Medium: makes corrections and batch work easier | Small | Good companion changes to bookmark filtering |
| 6 | Open the last workspace, keeping Overview available | Medium for repeat use | Small | Prefer this over building a second full workflow in the popup |

The bookmark page currently offers a folder tree but no search, age filter, or visible recency. Its flattened bookmark model also discards creation and last-used dates. Chrome provides `dateAdded` and optional `dateLastUsed` through the existing bookmarks permission; `dateLastUsed` is available from Chrome 114, below this extension's declared baseline. Label it **“Bookmark last opened”**, keep missing dates separate, and do not equate it with the last visit to the website. See the [bookmarks API](https://developer.chrome.com/docs/extensions/reference/api/bookmarks#type-BookmarkTreeNode).

The current confirmation lists site hosts and selected bookmark counts, but not the selected bookmark titles/paths or how many unselected bookmarks still use each affected site. A concise message such as “2 other bookmarks use this site; clearing its data affects them too” would be valuable. Site storage is shared across pages, so explain that deleting one bookmark cannot isolate that bookmark's portion of the website's storage. The [browsingData API's origin scope](https://developer.chrome.com/docs/extensions/reference/api/browsingData#specific-origins) supports this distinction.

Keep Bookmarks the primary entry point and Site data as a secondary capability. There is no clear return from expanding the extension into a general browser maintenance suite.

## What should stay

- **Small architecture:** native TypeScript modules, no runtime dependencies, and clear separation between UI, plan execution, browser operations, and job coordination. A framework migration has little demonstrated value.
- **Local processing:** packaged assets, no target-site previews or remote favicons, no analytics in the inspected runtime, and cookie values discarded from the inventory model.
- **Destructive-operation safeguards:** explicit review, data cleanup before bookmark removal, dependent bookmarks retained after a category fails, empty-folder checks, no recursive `removeTree`, and one active coordinated job.
- **Interruption behavior:** saved running jobs become unverified after worker restart and are not replayed automatically. Keep that conservative policy. Chrome explicitly advises designing for unexpected [service-worker termination](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).
- **Usable foundations:** native controls, accessible names, visible focus outlines, reduced-motion handling, protected-folder handling, and meaningful browser tests. The blue/white visual identity is coherent; another visual redesign is low priority.

## Public-release and maintenance priorities

Update store screenshots and descriptions alongside the next package. The returned listing still mentions AppCache, plugin data, and WebSQL, whereas this checkout intentionally removed those choices. Lead with the bookmark-and-data use case and use a short explanation of sign-out and unsynced-data consequences. Do not imply complete browser-trace removal. The fetched store results disagree on user count, so no audience-size conclusions are drawn here.

Provide an easy-to-find privacy explanation: what stays local, why bookmarks and browsing-data permissions are needed, why cookie/site access is optional, and how optional history is used. This is a trust recommendation; this review does not establish whether a separate existing privacy policy satisfies store requirements.

Add targeted regressions for the defects above, then a real worker-stop/reopen test and a saved-bookmark-change-after-review test. Run the release package on a supported Chrome installation and document the result. A small repeatable release command/checklist is sufficient; a large CI matrix, telemetry service, or new testing framework is not justified by the current size.

Clean up existing documentation and CSS when touching them. In particular, `docs/architecture.md` still describes a modal details dialog that locks the background, while the current implementation is a nonmodal aside sharing page scrolling. `app.css` and `drawer.css` also contain successive overrides of the same components. Consolidation can reduce later editing mistakes, but it should follow correctness work.

## Defer unless users demonstrate a need

- Scheduled or automatic deletion: substantial false-positive, recovery, and support complexity for an inherently destructive feature.
- Rich quick-clean popup: duplicates UI state and review logic while serving a different task from old-bookmark cleanup.
- AI classification, screenshots, live previews, remote favicons, and broken-link crawling: introduce network activity, permissions, false positives, or dependencies without a demonstrated advantage for the main task.
- Cloud sync/accounts, a general bookmark organizer, and exact storage-byte reporting: ongoing infrastructure or platform limitations outweigh near-term benefit.
- Full undo for website data: do not offer a restoration guarantee the browser cannot reliably fulfill. Start with bookmark export.
- Framework migration, dark mode, another rebrand, and elaborate animation work: lower value than finding the right bookmarks and safely clearing the reviewed data.
